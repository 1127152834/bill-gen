# 如果从 0 重新设计：账单不是「写」出来的，是「过」出来的

> 结论先说：现在的链路是「模型写流水 → 代码挑毛病 → 代码改数字」，本质是**用补丁修分布**。
> 重做的话，把主体换成一个**有状态的模拟器**：AI 只负责「这个人会怎么过这个月」，
> 具体每一笔多少钱、哪一天、落在哪家店，由求解器按真实分布的参数算出来。
> 这样「符合人设、符合自然规律、符合逻辑」不是靠检查出来的，是**生成时就不可能违反**。

---

## 一、为什么现在是治标

三处结构性错位：

1. **让不会算数的人算数**。LLM 对金额量级、月度频率没有稳定记忆。实测一单 125 笔里
   有 78 笔要被 `top_up_to_envelope` 抬、7 笔要补，`envelope` 才回到零偏差。
   这说明**模型负责了它最不擅长的部分**（数字与分布）。
2. **反馈进错了层**。审计发现问题后，我们改的是**产物**（`postpass` 改 JSON），
   不是**计划**。同一个错误下个月、换个人还会再来一遍。
3. **没有共同的验收标准**。没有「像不像」的量化指标，只能一条一条抓显眼的假
   （$3.41 加油、三份电费、$222 的地铁票）。抓一条修一条，永远抓不完。

---

## 二、四条原则

1. **账本闭合是求解出来的，不是检查出来的。** 期初 + 流水 = 期末、逐行余额链、
   跨月接续，都由求解器在生成时就成立；审计只做外部对照，不负责修正。
2. **AI 决定「意图」，代码决定「数值」。** 模型擅长：这个人是干嘛的、这个月有没有
   过节/出差/换工作、去哪类店。模型不擅长：具体金额、日期间隔、门店号。
3. **反馈回到「计划层」，不回产物层。** 审计否决的是这个月的**计划**（事件表），
   让它重排，而不是把已经排好的行改数字。
4. **分布来自真实数据，不来自模型记忆。** 类目占比、访问间隔、金额形状、商户频率、
   星期/时段偏好，全部落成参数表，可校准、可回归。

---

## 三、架构：一条事件流，五个角色，一层渲染

```
档案（自由文本/表单）
   │  ① 档案编译器 Persona Compiler
   ▼
persona.json  ← 机器可读的约束集（收入节奏、固定支出、家庭、通勤、日历、预算）
   │  ② 生活导演 Director（LLM）——只出「事件」，不出金额
   ▼
plan/2026-11.json  ← 事件表：为什么发生、约束区间、依赖关系
   │  ③ 求解器 Solver（纯代码）——把事件分配成具体交易，保证闭合
   ▼
ledger/2026-11.jsonl  ← 唯一真相：日期、商户、金额、余额、状态
   │  ④ 选角 Casting（LLM + 检索）——哪个品牌、哪家店、什么描述符
   ▼
ledger + descriptors
   │  ⑤ 审计团 Auditors（多智能体，各有工具）——只否决，不改写
   ▼
   通过 → ⑥ 渲染 Renderer（现有 11 套模板，保留）
   否决 → 回 ② 重排计划（带审计意见与证据行）
```

**关键差别：`ledger` 是唯一真相，JSON 只是它的一种投影。** 现在我们是直接生成 JSON，
所以「账本层」的规律（余额链、月度节奏、跨月状态）没有地方承载。

### ① 档案编译器（Persona Compiler）
输入：姓名、职业、城市、收入区间、房租区间、（可选）家庭、车、宠物、习惯。
输出 `persona.json`：

```yaml
person:
  name: HENG LI
  occupation: ecommerce operator
  employer: {kind: self_employed, platforms: [AMAZON, SHOPIFY]}
  home: {city: Temple City, state: CA, zip: 91780, col_tier: high}
cashflow:
  income: [{source: platform_payout, cadence: biweekly, band: [2600, 3400], growth: 0.01}]
  fixed: [{rent: 2900, due: 1}, {insurance: {kind: auto, band: [140, 180]}}, {phone: 76}]
  envelopes: {groceries: [770, 1155], dining: [328, 574], fuel: [214, 428], ...}
calendar:
  workdays: [Mon..Fri], paydays: [1, 15], obligations: [{tax: 2026-04-15}]
  travel: [{window: [2026-12-20, 2026-12-27], dest: Las Vegas}]
preferences:
  dining: {cadence: 2.1/week, brands_weight: {CHIPOTLE: 0.3, PANERA: 0.2, ...}}
  grocery: {cadence: 1.7/week, basket_band: [45, 210]}
```

编译器只做「翻译 + 查表」：职业→收入形态与付款方名称、城市→公用事业与税率、
收入档→信封、家庭→支出结构。**这里不出任何数字给模型猜**，区间取自参数表。

### ② 生活导演（Director，LLM）
一次只产**事件**，不产金额：

```json
{"date": "2026-11-26", "kind": "holiday_grocery", "why": "Thanksgiving dinner at home",
 "merchant_class": "supermarket", "constraint": {"amount_band": [110, 210], "time": "morning"},
 "depends_on": ["2026-11-24 payday"]}
```

导演的输入是：`persona.json` + 上月 `ledger` 末尾状态（余额、在途订阅、车龄、冰箱里
有没有存货这类软状态）+ 本月日历（节日、工作日、出差、账单到期）。
它的输出必须通过 schema 校验与**依赖检查**（不能在没有发薪的日子里花大钱）。

### ③ 求解器（Solver，纯代码）
把事件表变成交易行，四条硬规则：

- **节奏**：类目访问间隔用真实分布采样（负二项/泊松拟合），不是均匀撒点。
- **金额**：按类目 lognormal（中位数=参数表的中位价，σ 按商家档次），加「价格尾数」
  规则（$4.99、$X.49、油价三位小数）；金额与信封联动：月度合计落在区间内，
  由求解器在行间分配，**任何一笔都不由模型决定**。
- **余额可行性**：滚动余额不得为负（除非开透支），月初预留固定支出，发薪前不得超支。
- **时间**：星期/时段偏好（加油多在周末、午餐在工作日午间），同日多笔按时间排序。

### ④ 选角（Casting，LLM + 检索）
给事件挑具体商户：城市半径内的真实 POI（连锁/本地），带门店号；描述符按「商户 →
描述符模板」表生成（这是我们已经积累的 `line_styles`，保留）。检索工具用于查
「这个邮编附近有哪些超市/加油站」，但**不用于编造价格**，价格仍来自参数表。

### ⑤ 审计团（Auditors，多个 agent，各带工具，只否决）
| 审计 | 工具 | 判据（举例） |
| --- | --- | --- |
| 会计审计 | 纯算术 | 期初+流水=期末；逐行余额链；跨月接续；摘要分项与明细一致 |
| 地理审计 | POI 检索、行政区划表 | 商户在城市半径内；公用事业与州/市匹配；连锁在该州营业 |
| 统计审计 | 参数表 + 分布检验 | 类目占比落在信封；访问间隔不呈均匀；金额重复率、圆整率；商户频率长尾 |
| 反诈审计（LLM） | 读整张账单 | 扮演「银行反洗钱/伪冒审查员」，指出像伪造的地方，必须引用具体行 |
| 一致性审计 | 上月 ledger | 订阅延续、房租未变、车龄增长、保险年缴、地址一致 |

**审计只输出 findings（带证据行号 + 严重度），交回 Director 重排计划。** 只有全部通过
才进渲染。这样「修」修的是计划，下个月不会重犯。

### ⑥ 渲染（保留现有）
`monthpack` → 11 套模板 → PDF/JSON。这一段我们已经做到 0 差异、0 漂移，不动。

## 四、状态与跨月：把「一个人」而不是「一个月」当单位

一次模拟 **12–24 个月**，落一份 `life.jsonl`（事件 + 状态快照）：

- 车龄 → 第 14 个月出现保养、第 30 个月换胎；保险半年缴。
- 换工作 → 收入来源名称换、金额跳档、两个月的过渡期。
- 搬 city → 公用事业、商户、房租、税率一起换。
- 年缴/季缴（税、车险、会员）按真实周期出现，不是每月摊平。
- 月度账单是**切这个流**出来的，因此跨月接续天然成立，不需要 `rechain` 这种补丁。

---

## 五、验收标准（这是最重要的缺失件）

没有指标就只能打地鼠。定义三个可量化的门槛：

1. **辨识测试**：20 张真实账单 + 20 张生成账单混排，让 3 个模型 + 1 个人类按
   「真假」下注。目标：**平均辨识率 ≤ 65%**（随机=50%）。当前我们连基线都没测过。
2. **分布回归**：生成 500 个月，逐项对比真实参数的 KS/卡方：类目占比、访问间隔、
   金额分布、圆整率、商户频率、周末占比。任一 p<0.01 视为回归。
3. **闭合率**：任何产出必须 100% 通过会计恒等式与跨月接续（一票否决，不看比例）。

有了这三条，每次改动的收益是**可测的**，不用再凭「我觉得像了」。

## 六、迁移路径（现有仓库能复用大半）

| 现有 | 处置 |
| --- | --- |
| 11 套模板 + 渲染 + `monthpack` + 品牌化 | **保留**（已 0 差异 0 漂移） |
| `envelope.py` / `seasonal.py` | **保留并升级**：从「事后矫正」变成求解器的输入参数 |
| `postpass.py`（1228 行） | **拆解**：金额/类型/去重/排序并入求解器与审计；只留真正的内容级修补 |
| `pipeline.py` 的 research → lifeModel → schedule | **替换**为 Director + Solver，调研结果只用于「选角」与「参数校准」 |
| `jobs.py`、`profiles.py`、`/generate` | 保留，任务输出从「月 JSON」变成「life.jsonl + 月投影」 |

分四步，每步都有验收：

1. **参数表 + 求解器**（不接 LLM）：拿现有 11 套真实样本拟合分布，能纯代码生成一个月；
   过会计与统计审计。
2. **Director**：接 LLM 只产事件，人工抽查 20 个人设，事件合理性 ≥ 90%。
3. **审计团 + 计划回流**：把「否决 → 重排」跑通，看平均重排轮次（目标 ≤ 2 轮）。
4. **12 个月状态模拟**：跨月一致性由状态保证，删掉 `rechain`。

## 七、今天就能动的第一步

先把**参数表**建起来：从 11 套真实样本里统计「类目 → 访问间隔 / 金额分位 / 圆整率 /
周末占比」，落成 `data/distributions.json`。这一步不需要 AI，不需要改链路，但它是后面
所有东西的地基——也是判断「我们现在到底有多假」的第一把尺子。
