# 接入手册：把一个「没有 AI 的账单生成器」改成 Agent 流水线

> 读者：你的生成器已经能出片，但内容是人手写死或用模板填的。你要接 Agent，但不想推倒渲染器。
> 结论先给：**渲染器一个字都不用改，Agent 全部工作在渲染之前**。

## 1. 现状与目标

```
现在：  档案/手填 ──► 你的规则 ──► 账单数据 ──► 模板渲染 ──► PDF
目标：  档案 ──► [ Agent 层 ] ──► 账单数据 ──► 模板渲染 ──► PDF
                     ↑
                 契约（唯一格式权威）
```

Agent 层只做三件事：**想事件**（导演）、**算数值**（求解器，纯代码）、**挑名词**（选角）。
格式全部由契约决定，渲染器照旧。

## 2. 你的应用只需要暴露 4 个接口

| 接口 | 签名（语言无关） | 谁调 | 说明 |
| --- | --- | --- | --- |
| `read_contract(account)` | `account_id -> contract_json` | 每个 Agent | 契约是只读的；不许在 Agent 里改规则 |
| `emit_plan(persona, month)` | `-> plan_json` | 导演 | 事件列表，含 `type`/`date`/`place`/`party`/`deps`，**无金额** |
| `solve(plan, persona)` | `-> ledger_rows[]` | 求解器 | 纯代码：分配金额/日期/余额，构造即闭合 |
| `render(account, month_data)` | `-> pdf_bytes` | 投影 | 你现有的渲染器，不改 |

再补两个工具函数（可以是一个脚本）：
- `lint(contract, data) -> problems[]` —— 就是 `tools/statement_lint.py`；
- `conform(contract, data) -> counts` —— 按契约整形（去城市、去 `PAYMENT` 尾巴、截断、归一 Type）。

**关键约束**：`conform` 全流程只能有**一次**执行点，且必须在 `lint` 之前。到处 conform = 到处特判 = 三个月后没人看得懂。

## 3. 分期上线（每期都有可验收的产出）

| 期 | 内容 | 你的工作量 | 验收 |
| --- | --- | --- | --- |
| **L0** | 契约 + lint（无 AI） | 1–2 天 | 现有产物 lint 全绿 |
| **L1** | 导演 Agent 出 `plan.json`，金额仍用你的老规则 | 1 天 | 5 次跑：类目构成/间隔/节日覆盖在区间内 |
| **L2** | 求解器替换老规则（纯代码） | 2–3 天 | 闭合率 100%，余额链逐行连续 |
| **L3** | 选角 Agent（只挑名词） | 1 天 | 同城同州、品牌轮换、无占位名 |
| **L4** | 审计团 6 个（只否决）+ 回退路由 | 2 天 | 注入的 20 个错例，全部被对应审计抓到 |

**不要跳**：L1 之前不接选角，L2 之前不接审计。理由：审计的判据依赖求解器的不变量，求解器不存在时审计只能「凭感觉说不对」，那种 Agent 只会浪费时间。

## 4. 提示词怎么写（三条硬规矩）

1. **写清「你不许做什么」比写「你要做什么」更重要。**
   导演的提示词里最值钱的一句是「不要输出任何金额字段」；选角的最值钱一句是「不要改金额，不要改日期」。
2. **每个 Agent 都要有「输入 / 输出 / 硬规则 / 失败时怎么办」四节。**
   `kit/prompts/` 里每个文件都是这个结构，`tools/check_agents` 式的校验可以照抄：缺小节就不许上线。
3. **给枚举，不给形容词。**
   「写得自然一点」没用；「`type` 只能取 `Card / ACH Out / ACH In` 三个值之一」有用。

## 5. 结构化输出与重试

- 所有 Agent 输出 **JSON**，用 JSON Schema 校验（`kit/schemas/`）。
- 校验失败的处理顺序：① 把「上次输出 + 校验错误」拼成一条消息让它修（最多 2 轮）→ ② 仍失败则**降级**：导演降级为「模板事件序列」，选角降级为「契约里的 merchant 词表」。
- **不要**在失败时让模型「自由发挥」，那是最容易出假数据的地方。

## 6. 幂等与可重放

- 所有随机性来自 `seed`（建议 `seed = sha256(profile_id + month + template)`），同一 seed 必须产出同一份数据。
- 把 `seed`、契约 `sha256`、模型名、token 用量写进 `manifest.json`。出了假数据要能回答「哪一版规则、哪一个模型、第几次重试」。

## 7. 成本与延迟（实测口径，可按你的规模缩放）

| 环节 | 单次调用 | 一次「一账户 × 3 个月」的量级 |
| --- | --- | --- |
| 导演 | 1 次/月，输出 1–3k tokens | 3 次 |
| 选角 | 1 次/月（或按 20 行一批） | 3–6 次 |
| 审计 | 6 个角色，可只对「有疑点」的月跑 | 0–18 次 |
| 求解/渲染 | 0 次 | — |

本仓库实测：一账户两月真跑 `llmCalls 7`、`prompt 22015 / completion 7433` tokens。**不要**让模型逐行生成流水——那是成本与假数据的双重灾难。

## 8. 失败与回退

| 现象 | 处理 |
| --- | --- |
| lint 不过 | 拒绝出片，把 problems 原文抛回上一环，别自动改 |
| 审计否决 | 按 `findings.evidence` 回退：格式 → 选角；计划 → 导演；数值 → 求解器 |
| 模型超时/限流 | 退避 0.8/1.6/3.2s + 抖动；仍失败则降级到词表/模板事件，**不中断整个任务** |
| 契约缺失 | 直接失败（`没有 <account> 的账单契约`），不许拿相近账户凑 |

## 9. 可观测性（出问题时最救命的东西）

每个任务写一份 `job-summary.json`：

```json
{"job":"...","account":"chase-personal","months":["2026-11"],
 "seed":"...","contract_sha256":"...","model":"...",
 "stages":{"director":{"ms":3211,"tokens":{}},"solver":{"ms":8},"cast":{"ms":2210},"audit":{"findings":2}},
 "counts":{"rows":23,"conformed":3,"lint_problems":0},
 "warnings":["契约 open_questions 非空：BoA 无参考件"]}
```

日志用「阶段 + 人话」的格式：`director 计划 23 个事件`、`solver 生成 23 行，闭合校验通过`、`lint 0 问题`。
不要打 JSON 一大坨——人被叫去看日志的时候已经很不爽了。

## 10. 什么时候算「接好了」

- 关掉模型，系统仍能跑（降级路径完整）；
- 打开模型，产物比关掉时**明显更像**（用 `05-evaluation.md` 的盲测证明，别凭感觉）；
- 任意一份产物，都能追到「契约哪条规则 / 哪个 Agent / 哪个 seed」；
- 新增一家银行 = 加一份契约 + 一份 skill，**不改代码**。
